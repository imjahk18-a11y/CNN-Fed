# Phase 5A · A6000 기반 2-client FedAvg

linuxserver2의 NVIDIA RTX A6000 한 장에서 각 CUDA 클라이언트가 별도 프로세스로 추론 및 학습했다. Ground Server는 별도 CPU 프로세스에서 두 상태를 복원하고 집계했다. 별도 장치 두 대의 처리율, 전력, 온도, 무선망 및 Jetson 통합 메모리 검증은 PENDING_HARDWARE다.

## 동일 예산의 10라운드 비교

|모델|전송|파라미터|초기 mIoU|10R mIoU|총 TCP 앱 MB|평균 라운드 s|평균 글로벌 업데이트 L2|
|---|---|---:|---:|---:|---:|---:|---:|
|0%|FP32|9,526|37.13%|23.73%|1.8038|7.034|0.1379|
|0%|INT8|9,526|37.13%|24.41%|0.6634|7.220|0.1741|
|20%|FP32|6,376|30.99%|24.58%|1.2856|7.178|0.1245|
|20%|INT8|6,376|30.99%|25.61%|0.5379|7.306|0.1496|

0% 프루닝에서 INT8은 FP32 대비 앱 바이트를 63.2% 줄였다. 최종 mIoU 차이는 +0.68%p, 평균 라운드 시간 차이는 +0.186초였다.

20% 프루닝에서 INT8은 FP32 대비 앱 바이트를 58.2% 줄였다. 최종 mIoU 차이는 +1.03%p, 평균 라운드 시간 차이는 +0.127초였다.

20% 프루닝과 INT8을 결합하면 원본 FP32보다 총 통신량이 70.2% 줄었다. 네 조건 모두 최종 mIoU가 자기 초기값보다 낮았고, 두 모델 모두 INT8의 평균 업데이트 L2가 FP32보다 컸다. 이 배치 1 실험에서는 작은 업데이트가 INT8의 최종 성능을 설명한다는 가설을 지지하지 않는다.

각 모델·코덱은 같은 seed 42, Non-IID 분할, 클라이언트당 96패치 × 1 epoch × 10라운드, 배치 1, AdamW 0.0001, FP32 연산을 사용했다. 초기 및 종료 성능은 장면 12의 144패치에서 유효 복셀 혼동행렬로 계산했다. 합집합이 0인 클래스는 평균에서 제외했다. 클라이언트 1은 장면 3, 클라이언트 2는 장면 4를 사용했다. WMSC는 사용하지 않았다. 서버는 한 클라이언트씩 요청한다. 한 시드와 한 분할에서 얻은 라운드 시간에는 파일 로드, GPU 학습, CPU 검증, 프로세스 스케줄링이 포함된다. 체크포인트 디스크 쓰기와 최초 프로세스 기동은 라운드 타이머 밖이다.

0.3 m, XY 32×32, Full-Z 점유 좌표는 7점 이웃과 풀링·복원에 쓰인다. 입력 특징은 RGB-16 대표색 3채널을 255로 나눈 값이다. 6개 클래스의 순서는 Ground, Building, Tree, Car, Light pole, Fence다. 채널 폭은 원본 16→32→16, 프루닝 13→26→13이다. 기존 Phase 3/4의 배치 24와 비교하면 배치 1에서 패치당 최적화 횟수와 BN 통계가 달라진다. 이 실험만으로 정확도 차이의 원인을 분리할 수 없다.

서버와 클라이언트는 양방향으로 전체 상태를 전송한다. INT8은 텐서별 max(abs)/127 스케일과 nearest-even 반올림을 사용하며 0 텐서의 스케일은 1이다. BN running mean/variance도 압축한다. 수신측이 FP32로 복원한 뒤 샘플 수로 FedAvg하며 정수 BN 카운터는 최대값을 쓴다. 업데이트 L2는 연속 글로벌 모델의 학습 파라미터 차이이며 BN 버퍼를 제외한다. TCP 앱 바이트에는 양방향 프레임, 접속 인사와 종료 확인을 포함했다. TCP/IP 헤더나 링크 계층 재전송은 집계 대상 밖이다.

## 재시작과 연결 단절

- FP32에서 1R 커밋 후 서버 프로세스를 종료하고 새 PID로 재시작했다. 2R에서 클라이언트 2의 업로드 전 연결을 끊었다. 저장된 응답을 1회 재전송했고, 정상 2R 모델과 모든 파라미터·버퍼가 정확히 일치했다. 추가 앱 바이트는 45,170, 단절 감지 후 접속 수락까지 0.401초였다.
- INT8에서 1R 커밋 후 서버 프로세스를 종료하고 새 PID로 재시작했다. 2R에서 클라이언트 2의 업로드 전 연결을 끊었다. 저장된 응답을 1회 재전송했고, 정상 2R 모델과 모든 파라미터·버퍼가 정확히 일치했다. 추가 앱 바이트는 16,623, 단절 감지 후 접속 수락까지 0.401초였다.

## 로컬 추론과 학습 병행

## 클라이언트 메모리 예산

프로세스별 PyTorch 예약 한도는 4 GiB 시나리오에서 2 GiB, 8 GiB에서 6 GiB로 설정했다. 두 시나리오 모두 OS를 위해 1 GiB를 남긴다는 가정이다. 작업 메모리 지표는 호스트 프로세스 RSS 최고치 + CUDA 예약 최고치 + max(0, NVIDIA 드라이버 표본 − 같은 시점의 CUDA 예약량)이다. 각 항의 시점이 다르고 드라이버는 표본 한 개여서 실제 통합 메모리 최고치를 나타내지 않는다.

배치 1·2·4의 모든 값은 jetson_budget_checks.csv에 있다. 단일 클라이언트 벤치마크는 모델·예산·클라이언트마다 새 프로세스로 순차 실행했다. FL 세션 중 각 클라이언트의 실제 메모리는 jetson_resource_usage.csv에 따로 기록했다. 공유 A6000에서 작업을 겹쳤을 때의 결과이며 보드에서의 전력, 온도, 처리속도, 비행 제어와의 공존은 PENDING_HARDWARE다.

## 재현

측정 환경은 Ubuntu 22.04.5 LTS, Python 3.11.3, PyTorch 2.8.0+cu126, CUDA 런타임 12.6이다. 기존 결과 파일 4,041개의 실행 전후 SHA-256이 일치했다. 모델 체크포인트 SHA는 jetson_model_comparison.csv, 분할과 검증 번들 SHA는 jetson_environment.json에 있다. 데이터와 가중치는 실험 서버에 보관한다.

```bash
cd /home/gpu_01/voxel_uav_project
.venv-gpu/bin/python -m experiments.jetson_virtual
.venv-gpu/bin/python -m experiments.jetson_virtual_bench
.venv-gpu/bin/python -m experiments.jetson_virtual_report
.venv-gpu/bin/python -m pytest -q
```

완료된 FL 및 벤치마크 조건은 재실행 시 건너뛴다. 독립 재측정은 기존 Phase 1~4 자료만 갖춘 새 작업 디렉터리에서 같은 설정으로 실행한다. 보드 배포 준비와 역할별 명령은 [Jetson 실행 안내](../../deployment/JETSON.md)에 있다.
